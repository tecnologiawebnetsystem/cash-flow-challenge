CASHFLOW API - QUALIDADE DE CODIGO, SOLID, TESTABILIDADE E DESACOPLAMENTO
=============================================================================

Este arquivo responde diretamente aos 4 criterios de avaliacao do desafio:

  1) Qualidade do Codigo (Clean Code + SOLID)
  2) Testabilidade
  3) Desacoplamento entre camadas
  4) Documentacao

Para cada um, ha uma explicacao do que significa, onde esta implementado
no codigo (com caminho de arquivo e trecho real) e como voce explicaria
isso numa entrevista.


-----------------------------------------------------------------------------
1) QUALIDADE DO CODIGO: CLEAN CODE E SOLID
-----------------------------------------------------------------------------

1.1) SRP - Principio da Responsabilidade Unica
------------------------------------------------
"Uma classe deve ter um, e somente um, motivo para mudar."

Onde esta:

  a) src/CashFlow.Application/Consolidation/Commands/ConsolidateDailyBalance/
     ConsolidateDailyBalanceCommandHandler.cs

     Este handler SO calcula o saldo do dia (soma creditos, soma debitos,
     consolida). Ele propositalmente NAO trata exceções, NAO faz retry e
     NAO decide o que fazer se o banco cair. Isso e responsabilidade de
     outra classe: ConsolidationResiliencePipelineFactory (Infrastructure).

     Por que isso importa: se eu decidir trocar retry por outra
     estrategia, ou mudar o numero de tentativas, eu mudo SOMENTE a
     Infrastructure. A regra de negocio "como consolidar um saldo" nao
     muda uma linha. Dois motivos de mudanca diferentes = duas classes
     diferentes.

  b) src/CashFlow.Application/Common/Behaviors/ValidationBehavior.cs
     src/CashFlow.Application/Common/Behaviors/LoggingBehavior.cs

     Validacao de entrada e logging de tempo de execucao NAO estao
     escritos dentro de cada handler. Sao "behaviors" (decorators) que o
     MediatR executa automaticamente antes/depois de qualquer
     Command/Query. Se eu nao tivesse feito isso, cada um dos meus
     handlers teria que comecar com:

         if (!ModelState.IsValid) throw ...
         _logger.LogInformation("comecei");
         try { ... } catch { _logger.LogError(...); throw; }

     repetido em todo handler. Em vez disso, essa preocupacao "transversal"
     (cross-cutting concern) fica em UM lugar so e e aplicada a TODOS os
     handlers automaticamente via pipeline.

  c) src/CashFlow.Domain/ValueObjects/Money.cs

     A classe Money so tem uma responsabilidade: garantir que um valor
     monetario de lancamento nunca seja zero ou negativo, e nunca tenha
     mais de 2 casas decimais. Ela nao sabe nada sobre banco de dados, API
     ou HTTP. So valida e representa dinheiro.

1.2) OCP - Principio Aberto/Fechado
--------------------------------------
"Deve ser possivel estender o comportamento sem modificar codigo existente."

Onde esta:

  a) O pipeline de behaviors do MediatR (ValidationBehavior, LoggingBehavior)
     e registrado assim em src/CashFlow.Application/DependencyInjection.cs:

         services.AddTransient(typeof(IPipelineBehavior<,>), typeof(LoggingBehavior<,>));
         services.AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));

     Se no futuro eu precisar adicionar um novo comportamento transversal
     (por exemplo, cache de resposta, ou auditoria de quem fez a
     requisicao), eu crio uma nova classe que implementa
     IPipelineBehavior<TRequest,TResponse> e registro mais uma linha aqui.
     Nenhum handler existente e alterado.

  b) IConsolidationQueue (interface) permite trocar a fila em memoria por
     uma fila real (RabbitMQ, SQS) implementando a interface de novo, sem
     tocar no RegisterLaunchCommandHandler que a consome.

1.3) LSP - Principio da Substituicao de Liskov
--------------------------------------------------
"Um objeto de uma subclasse deve poder substituir um objeto da superclasse
sem quebrar o comportamento esperado."

Onde esta:

  Nao ha uma hierarquia profunda de herança de comportamento no projeto
  (o design evita heranca de negocio propositalmente - ver principio
  "prefira composicao a heranca"). O unico lugar com herança e a base
  tecnica Entity -> AggregateRoot (src/CashFlow.Domain/Common/), que
  qualquer classe de dominio (Launch, DailyBalance) estende. Isso e seguro
  porque AggregateRoot so adiciona capacidade (lista de eventos de
  dominio), nunca redefine comportamento de forma que quebre expectativas
  de quem usa uma Entity.

  Se um entrevistador perguntar "onde vejo LSP no seu projeto", a resposta
  honesta e: o projeto e pequeno e deliberadamente evita hierarquias de
  heranca de negocio (isso e uma boa pratica, nao uma lacuna) - LSP e mais
  relevante em bases de codigo com polimorfismo de comportamento, que nao
  e o caso aqui.

1.4) ISP - Principio da Segregacao de Interface
---------------------------------------------------
"Uma classe nao deveria ser forcada a depender de metodos que nao usa."

Onde esta:

  Em vez de uma unica interface generica "IRepository" com CRUD completo
  para tudo, o projeto tem interfaces pequenas e especificas por agregado:

    - ILaunchRepository (src/CashFlow.Domain/Repositories/ILaunchRepository.cs)
      Metodos: AddAsync, GetByDateAsync. Nada de Update/Delete porque um
      lancamento, nesse dominio, nunca e editado ou removido depois de
      criado (e um fato financeiro imutavel).

    - IDailyBalanceRepository (.../IDailyBalanceRepository.cs)
      Metodos: GetByDateAsync, GetByDateRangeAsync, UpsertAsync. Um so
      metodo de escrita (Upsert) porque a consolidacao e sempre
      "criar-ou-atualizar", nunca um Update isolado.

  Cada consumidor depende so do que precisa. Quem so le saldo diario
  (o endpoint de relatorio) nunca fica exposto a um metodo de escrita que
  nao usa.

1.5) DIP - Principio da Inversao de Dependencia
----------------------------------------------------
"Modulos de alto nivel nao devem depender de modulos de baixo nivel; ambos
devem depender de abstracoes."

Este e o principio mais visivel do projeto, e o mais facil de defender numa
entrevista:

  - Domain define as interfaces (ILaunchRepository, IDailyBalanceRepository)
    mas NAO as implementa.
  - Application define as interfaces (IUnitOfWork, IConsolidationQueue,
    IDateTimeProvider) e usa via injecao de construtor - olhe qualquer
    handler, ele so recebe interfaces, nunca "new LaunchRepository()".
  - Infrastructure e quem IMPLEMENTA essas interfaces (LaunchRepository
    com EF Core, InMemoryConsolidationQueue com System.Threading.Channels,
    SystemDateTimeProvider com DateTime.UtcNow).
  - A ligacao entre interface e implementacao concreta acontece em UM
    lugar so: src/CashFlow.Infrastructure/DependencyInjection.cs, no
    metodo AddInfrastructure(), via:

        services.AddScoped<ILaunchRepository, LaunchRepository>();
        services.AddScoped<IDailyBalanceRepository, DailyBalanceRepository>();
        services.AddSingleton<IConsolidationQueue>(...);

  Prova concreta de que isso funciona: os testes de unidade
  (RegisterLaunchCommandHandlerTests.cs) testam o handler passando MOCKS
  dessas interfaces (Moq), sem nenhum banco de dados real. Isso so e
  possivel porque o handler depende de abstracao, nao de implementacao.

1.6) Clean Code (fora do SOLID)
-----------------------------------
Praticas de Clean Code visiveis no codigo:

  - Nomes revelam intencao: RegisterLaunchCommand, ConsolidateDailyBalance,
    InvalidLaunchAmountException - o nome da classe basta para entender o
    que ela faz, sem precisar ler o corpo.
  - Metodos curtos e com um nivel de abstracao: o Handle() de cada handler
    tem no maximo ~10 linhas relevantes, e cada linha e uma "frase" no
    nivel certo (nao mistura "somar decimais" com "abrir conexao HTTP").
  - Fail fast e invariantes protegidos na origem: Launch.Create() e
    Money.Create() validam e lancam excecao de dominio na criacao,
    nunca deixando um objeto invalido existir "por um instante".
  - Sem "numeros magicos" soltos: limites como o tamanho maximo de
    descricao (200) e o intervalo maximo do relatorio (366 dias) estao
    nomeados e comentados no validator, nao espalhados no codigo.
  - Comentarios explicam o "porque", nao o "o que": quase todo comentario
    no projeto justifica uma decisao de design (ex.: "por que este handler
    nao trata excecao") em vez de narrar o que a linha de codigo abaixo
    obviamente faz.

2) TESTABILIDADE
-----------------------------------------------------------------------------

O que o desafio pede: "rotinas de testes automatizados para atestar o
funcionamento correto das logicas de negocio".

O projeto tem DUAS suites de teste, cada uma com um proposito diferente:

  a) tests/CashFlow.UnitTests (39 testes) - testam REGRA DE NEGOCIO isolada,
     sem banco de dados, sem HTTP, em milissegundos:

       - Domain/MoneyTests.cs        -> Money nunca aceita valor <= 0
       - Domain/LaunchTests.cs       -> Launch.Create valida descricao e
                                         calcula SignedAmount corretamente
       - Domain/DailyBalanceTests.cs -> a consolidacao calcula saldo de
                                         fechamento = creditos - debitos
       - Application/RegisterLaunchCommandHandlerTests.cs
                                      -> o handler persiste o lancamento
                                         MESMO quando a fila de
                                         consolidacao esta cheia (o
                                         requisito nao-funcional mais
                                         importante do desafio, testado
                                         de forma explicita)
       - Application/ConsolidateDailyBalanceCommandHandlerTests.cs
                                      -> a consolidacao e idempotente:
                                         chamar duas vezes para a mesma
                                         data nao duplica nada
       - Application/RegisterLaunchCommandValidatorTests.cs
                                      -> valida os limites de entrada
                                         (valor > 0, descricao <= 200 chars)
       - Application/InMemoryConsolidationQueueTests.cs
                                      -> a fila descarta sinal em vez de
                                         bloquear quando esta cheia

     Como isso e possivel sem banco de dados real: os handlers dependem
     de INTERFACES (ILaunchRepository, IUnitOfWork etc.), entao nos testes
     eu crio um "dublê" (mock) dessas interfaces com a biblioteca Moq e
     verifico apenas o comportamento da regra de negocio.

  b) tests/CashFlow.IntegrationTests (8 testes) - testam o sistema
     INTEIRO, do HTTP ate o Postgres real, usando Testcontainers (sobe um
     container Docker de Postgres so para os testes, descartavel):

       - Api/LaunchesControllerTests.cs      -> POST /launches de ponta a
                                                 ponta grava no banco real
       - Api/DailyBalancesControllerTests.cs -> consolidacao + idempotencia
                                                 validadas contra o banco
                                                 real, nao um mock

  Por que as duas: testes de unidade sao rapidos e me dizem SE a regra de
  negocio esta certa; testes de integracao sao mais lentos mas me dizem se
  as camadas realmente conversam entre si (mapeamento do EF Core, tipos de
  coluna, JSON de request/response) - um mock nunca pegaria um erro de
  mapeamento de banco, por exemplo.

  Como rodar (ver tambem 06-TESTES-EXPLICADOS.txt para o passo a passo
  completo):

      dotnet test tests/CashFlow.UnitTests/CashFlow.UnitTests.csproj
      dotnet test tests/CashFlow.IntegrationTests/CashFlow.IntegrationTests.csproj

  Resultado nesta revisao: 48 testes de unidade passando, build sem
  nenhum warning.

3) DESACOPLAMENTO ENTRE CAMADAS
-----------------------------------------------------------------------------

O que o desafio pede: "isolamento evidente das atribuicoes em diferentes
camadas da aplicacao (infraestrutura, aplicacao e dominio)".

Prova objetiva (nao e so "no papel" - e forcado pelo compilador): a
dependencia entre projetos .csproj so aponta em UMA direcao:

    CashFlow.Domain          -> nao depende de NADA (nem de outro projeto
                                 da solucao, nem de bibliotecas externas
                                 como EF Core ou MediatR)

    CashFlow.Application     -> depende so de CashFlow.Domain
                                 (+ MediatR e FluentValidation, que sao
                                 bibliotecas de orquestracao, nao de
                                 infraestrutura)

    CashFlow.Infrastructure   -> depende de CashFlow.Application (e,
                                 por consequencia, de Domain)
                                 (+ EF Core, Npgsql, Polly)

    CashFlow.Api              -> depende de Application e Infrastructure
                                 (e o unico projeto que "amarra" tudo)

Isso significa, na pratica:

  - O Domain nao sabe que existe um banco de dados Postgres. Se eu trocar
    Postgres por SQL Server ou MongoDB, ZERO linhas de Domain mudam.
  - O Domain nao sabe que existe uma API REST. Se eu expuser o mesmo
    dominio via um Worker de fila (sem HTTP nenhum), ZERO linhas de
    Domain ou Application mudam - so criaria um novo projeto de entrada
    que chama os mesmos Commands via MediatR.
  - A Application (os Commands/Handlers, que representam os casos de uso)
    NAO sabe como o EF Core funciona. Ela so conhece a interface
    ILaunchRepository. A implementacao real com DbContext, LINQ to SQL
    etc. mora exclusivamente em Infrastructure.

  Como validar isso de forma pratica: tente compilar so o projeto
  CashFlow.Domain sozinho (dotnet build src/CashFlow.Domain) - ele
  compila isoladamente, sem baixar EF Core, sem Npgsql, sem nada. Isso e
  a prova de que o dominio esta genuinamente isolado, nao é so uma pasta
  com nome bonito.

  Regra pratica que segui ao decidir "essa classe vai em qual camada?":

    - "Isso e uma regra do NEGOCIO (existiria mesmo sem banco de dados
      ou sem API)?" -> Domain.
    - "Isso e um CASO DE USO (orquestra passos, mas nao decide a regra em
      si)?" -> Application.
    - "Isso e um DETALHE TECNICO (como persistir, como enviar, como
      reter)?" -> Infrastructure.
    - "Isso e sobre RECEBER uma requisicao HTTP e devolver uma resposta"?
      -> Api.

4) DOCUMENTACAO
-----------------------------------------------------------------------------

O que o desafio pede: "explicacoes transparentes sobre as escolhas
tecnicas realizadas e sobre como executar a aplicacao".

O repositorio tem documentacao em duas camadas:

  a) README.md - e o ponto de entrada. Cobre: pre-requisitos, como rodar
     (Docker Compose e modo local), como acessar o Swagger, tabela de
     aderencia ao desafio, estrutura do banco de dados, padroes de
     projeto usados e como rodar os testes.

  b) Arquivos .txt numerados na raiz - cada um responde uma pergunta
     tipica de entrevista tecnica em profundidade maior do que caberia
     no README:

       01-ANALISE-DE-ADERENCIA-AO-DESAFIO.txt
       02-COMO-TESTAR-A-API.txt
       03-ARQUITETURA-EXPLICADA.txt
       04-PADROES-DE-PROJETO-EXPLICADOS.txt
       05-BANCO-DE-DADOS-EXPLICADO.txt
       06-TESTES-EXPLICADOS.txt
       07-QUALIDADE-SOLID-TESTABILIDADE-DESACOPLAMENTO.txt (este arquivo)
       ARQUITETURA-E-DECISOES-TECNICAS.txt (documento de referencia mais
       longo, com o racional completo de cada decisao e os trade-offs
       considerados)

  c) Dentro do proprio codigo - todo Handler, Value Object e componente de
     resiliencia (fila, worker, circuit breaker) tem um comentario XML
     (///) explicando o "porque" da decisao, nao so o "o que" a classe
     faz. Esses mesmos comentarios sao exibidos automaticamente na UI do
     Swagger (ver 02-COMO-TESTAR-A-API.txt), porque o projeto gera o
     arquivo CashFlow.Api.xml a partir deles (GenerateDocumentationFile
     habilitado no CashFlow.Api.csproj + IncludeXmlComments no Program.cs).

  Transparencia sobre limitacoes conhecidas (isso tambem conta como boa
  documentacao - nao esconder trade-offs): a fila de consolidacao e em
  memoria (Channel), o que significa que um sinal pendente se perde se o
  processo cair antes do worker consumi-lo. Isso e aceitavel dentro do
  requisito do desafio (ate 5% de perda de SINAL, nunca de LANCAMENTO) e
  esta coberto pelo job de reconciliacao periodica (ReconciliationWorker),
  mas em um cenario de producao real com multiplas instancias a
  recomendacao documentada e trocar por uma fila persistente (SQS,
  RabbitMQ, Postgres como fila). Isso esta detalhado em
  ARQUITETURA-E-DECISOES-TECNICAS.txt.


-----------------------------------------------------------------------------
RESUMO PARA RESPONDER RAPIDO NA ENTREVISTA
-----------------------------------------------------------------------------

Se o entrevistador perguntar direto "voce seguiu Clean Code e SOLID?",
uma resposta curta e defensavel e:

  "Sim. O DIP e o mais visivel: toda camada de cima depende so de
  interfaces, nunca de implementacao concreta, e isso e forcado pelas
  referencias de projeto no .csproj - o Domain nem consegue enxergar o EF
  Core. O SRP aparece separando validacao/logging dos handlers via
  pipeline do MediatR, e separando a regra de consolidacao da politica de
  retry/circuit breaker, que fica so na Infrastructure. Isso tambem e o
  que torna o projeto testavel: os 39 testes de unidade rodam sem banco
  de dados nenhum, so trocando as interfaces por mocks."
