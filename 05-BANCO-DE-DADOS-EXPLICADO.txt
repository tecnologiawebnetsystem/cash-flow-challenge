================================================================================
 BANCO DE DADOS EXPLICADO - para responder em entrevista
================================================================================

Banco usado: PostgreSQL 16, acessado via Entity Framework Core + Npgsql,
usando a abordagem "Code First": as tabelas nao foram desenhadas antes num
diagrama e depois copiadas para o codigo - elas nascem a partir das
entidades C# (Launch, DailyBalance) e das classes de configuracao do EF
Core, e o EF Core gera as migrations (scripts de criacao/alteracao de
tabela) automaticamente a partir disso.

Arquivos-fonte da verdade sobre o schema:
  - src/CashFlow.Domain/Entities/Launch.cs
  - src/CashFlow.Domain/Entities/DailyBalance.cs
  - src/CashFlow.Infrastructure/Persistence/Configurations/LaunchConfiguration.cs
  - src/CashFlow.Infrastructure/Persistence/Configurations/DailyBalanceConfiguration.cs
  - src/CashFlow.Infrastructure/Migrations/*_InitialCreate.cs (o script gerado)

--------------------------------------------------------------------------------
1. DIAGRAMA (visao simples)
--------------------------------------------------------------------------------

    +-----------------------------+
    |          launches           |
    +-----------------------------+
    | id            (PK, uuid)    |
    | description   (varchar 200) |
    | amount         (numeric)    |
    | type           (varchar)    |  "Credit" ou "Debit"
    | launch_date    (date)       |  <---+
    | created_at_utc (timestamp)  |      |
    +-----------------------------+      |
                                          | (relacao logica, NAO ha
                                          |  foreign key fisica)
                                          |
    +-----------------------------+      |
    |       daily_balances        |      |
    +-----------------------------+      |
    | reference_date (PK, date)  |  <----+  (agrupa por data)
    | total_credits   (numeric)   |
    | total_debits    (numeric)   |
    | closing_balance (numeric)   |
    | status          (varchar)   |  "Pending" / "Consolidated" / "Failed"
    | consolidated_at_utc (ts?)   |
    | failure_reason  (varchar?)  |
    | row_version     (bytea)     |  token de concorrencia otimista
    +-----------------------------+

Por que NAO existe uma foreign key literal entre launches e daily_balances:
daily_balances e uma tabela de PROJECAO/RESUMO (uma "materializacao" do
somatorio dos lancamentos de um dia), nao uma entidade filha no sentido
classico. A relacao entre elas e "por data" (reference_date = launch_date),
calculada pelo processo de consolidacao, e nao uma chave estrangeira fixa.
Isso e intencional: o saldo diario pode (e deve) ser recalculado do zero a
qualquer momento a partir dos lancamentos daquele dia - ele nunca e a
"fonte da verdade", so uma projecao derivada dela.

--------------------------------------------------------------------------------
2. TABELA "launches" (detalhada)
--------------------------------------------------------------------------------

  Coluna           | Tipo             | Regras
  ------------------|------------------|----------------------------------
  id                | uuid (PK)        | Gerado no codigo (Guid.NewGuid()),
                    |                  | nao pelo banco.
  description       | varchar(200)     | not null.
  amount             | numeric(18,2)    | not null. Sempre > 0 (a entidade
                    |                  | Money garante isso antes mesmo de
                    |                  | chegar no banco).
  type               | varchar          | not null. Guardado como texto
                    |                  | ("Credit"/"Debit"), nao como
                    |                  | numero, para o dado no banco ser
                    |                  | legivel por humanos direto no
                    |                  | psql, sem precisar traduzir enum.
  launch_date        | date             | not null. Indexado (index em
                    |                  | launch_date), porque toda consulta
                    |                  | de negocio filtra por data.
  created_at_utc      | timestamp       | not null. Preenchido em UTC no
                    |                  | momento da criacao.

  Por que "amount" e um numero simples na tabela, e nao uma tabela
  separada para o Value Object Money? Porque o EF Core mapeia Money como
  um "owned type" (tipo possuido) - ele existe como um objeto rico dentro
  do C# (com sua propria validacao), mas e "achatado" (flattened) em uma
  unica coluna decimal na tabela, sem criar uma tabela extra so para
  guardar um numero. Isso e configurado em LaunchConfiguration.cs.

--------------------------------------------------------------------------------
3. TABELA "daily_balances" (detalhada)
--------------------------------------------------------------------------------

  Coluna              | Tipo             | Regras
  --------------------|------------------|----------------------------------
  reference_date        | date (PK)       | Uma linha por data - a data EH
                       |                  | a chave primaria (nao existe um
                       |                  | id separado, porque so pode
                       |                  | existir um saldo consolidado
                       |                  | por dia).
  total_credits         | numeric(18,2)    | Soma de todos os creditos do dia.
  total_debits           | numeric(18,2)    | Soma de todos os debitos do dia.
  closing_balance        | numeric(18,2)    | total_credits - total_debits.
  status                 | varchar          | "Pending" | "Consolidated" |
                       |                  | "Failed" (enum ConsolidationStatus).
  consolidated_at_utc     | timestamp?      | Preenchido so quando status =
                       |                  | Consolidated.
  failure_reason          | varchar?        | Preenchido so quando status =
                       |                  | Failed (guarda a mensagem do
                       |                  | ultimo erro, para diagnostico).
  row_version              | bytea (rowversion) | Token de concorrencia
                       |                  | otimista - o EF Core incrementa
                       |                  | isso a cada UPDATE e rejeita
                       |                  | qualquer save baseado numa
                       |                  | versao antiga.

  Por que a data e a chave primaria, e nao um Guid/int autoincrement? Porque
  a regra de negocio e literalmente "um saldo consolidado por dia" - usar a
  propria data como chave torna essa regra impossivel de violar no nivel do
  banco (nao existe como ter duas linhas para o mesmo dia, o banco rejeitaria
  na hora por violacao de chave primaria).

--------------------------------------------------------------------------------
4. UPSERT (inserir OU atualizar) na consolidacao
--------------------------------------------------------------------------------

Toda vez que a consolidacao roda para uma data, ela faz um "upsert": se
ainda nao existe uma linha para aquela reference_date, insere; se ja
existe, atualiza os totais e o status. Isso e o que torna a consolidacao
IDEMPOTENTE - rodar a mesma data 10 vezes seguidas sempre resulta na mesma
linha final, nunca em 10 linhas duplicadas ou em totais somados errado.

Onde: IDailyBalanceRepository.UpsertAsync (Domain, interface) /
DailyBalanceRepository (Infrastructure, implementacao).

--------------------------------------------------------------------------------
5. INDICES
--------------------------------------------------------------------------------

  - launches.launch_date            -> toda consulta de negocio (listar
                                        lancamentos de um dia, consolidar um
                                        dia) filtra por essa coluna.
  - daily_balances (PK reference_date) -> a propria chave primaria já
                                        serve como indice para consultas de
                                        um unico dia; consultas por
                                        intervalo (startDate/endDate) usam
                                        um range scan sobre esse mesmo
                                        indice.

--------------------------------------------------------------------------------
6. MIGRATIONS (como o schema chega no banco)
--------------------------------------------------------------------------------

O schema nao e criado manualmente com um script SQL solto: ele vem de
"Migrations" do EF Core, que sao classes C# geradas automaticamente (em
src/CashFlow.Infrastructure/Migrations/), cada uma descrevendo uma
alteracao incremental do banco (criar tabela X, adicionar coluna Y, etc.).

Como elas sao aplicadas: em Program.cs, ao iniciar a API, e chamado
dbContext.Database.MigrateAsync(), que aplica automaticamente qualquer
migration pendente. Isso significa que, ao rodar "docker compose up", o
banco e criado e populado com o schema correto sem nenhum passo manual.

Para gerar uma nova migration (se voce alterar uma entidade), o comando
seria:

    dotnet ef migrations add NomeDaMudanca \
      --project src/CashFlow.Infrastructure \
      --startup-project src/CashFlow.Api

(existe CashFlowDbContextFactory.cs justamente para permitir esse comando
funcionar fora do processo normal da Api, "em tempo de design").

--------------------------------------------------------------------------------
7. PERGUNTAS DE ENTREVISTA SOBRE O BANCO
--------------------------------------------------------------------------------

P: "Por que Postgres e nao SQL Server / MySQL / Mongo?"
R: PostgreSQL e open-source, roda facil em container (Docker), tem otimo
   suporte no EF Core via Npgsql, e o modelo de dados aqui e claramente
   relacional (lancamentos e saldos agregados por data) - nao ha
   necessidade de um banco de documentos (Mongo) ou de features
   proprietarias de um SQL Server.

P: "Por que nao ha uma foreign key entre as duas tabelas?"
R: Porque daily_balances nao e uma entidade "filha" de launches no sentido
   tradicional - e uma projecao/resumo, recalculada a partir dos
   lancamentos daquela data sempre que a consolidacao roda. A ligacao e
   pela data em si, nao por uma chave estrangeira fisica.

P: "O que acontece se dois processos tentarem consolidar a mesma data ao
    mesmo tempo?"
R: O RowVersion (concorrencia otimista) garante que so um dos dois
   consiga salvar por vez; o outro recebe uma exception de concorrencia,
   que e absorvida pelo pipeline de retry do Polly - a proxima tentativa
   le a versao mais recente e tenta de novo.

P: "Como voce garante que o valor de um lancamento nunca fica negativo ou
    zero no banco?"
R: Isso e garantido ANTES de chegar no banco: o Value Object Money so pode
   ser criado atraves de Money.Create(...), que lanca uma exception se o
   valor for <= 0. E impossivel, no codigo, montar um Launch com um valor
   invalido para depois tentar salvar - a validacao acontece na camada de
   dominio, nao so numa constraint de banco (embora nada impeca de
   adicionar tambem um CHECK constraint no banco como camada extra de
   protecao, se quisesse reforcar ainda mais).
