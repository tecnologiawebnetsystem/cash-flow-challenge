================================================================================
 02 - COMO TESTAR A API (passo a passo, com exemplos reais)
================================================================================

Este arquivo e um roteiro pratico: como subir o projeto e testar cada
endpoint na mao, seja pelo Swagger (mais facil, visual, direto no navegador)
ou por linha de comando com curl. Inclui tambem os casos de erro esperados
e um roteiro para demonstrar, na pratica, que o registro de lancamentos
continua funcionando mesmo quando a consolidacao tem problema.

--------------------------------------------------------------------------------
1. SUBINDO O PROJETO
--------------------------------------------------------------------------------

OPCAO A - Docker Compose (a mais simples, recomendo essa)

    docker compose up --build

    O que esse comando faz, por baixo dos panos:
    - Sobe um container do Postgres 16 (usuario/senha/banco: cashflow) na
      porta 5432, com um healthcheck (pg_isready) que so libera a API depois
      que o banco estiver de fato pronto para receber conexoes.
    - Builda a imagem da API (o Dockerfile usa multi-stage: uma imagem com
      o SDK completo so para compilar, e uma imagem de runtime bem mais
      leve para executar) e sobe na porta 8080.
    - A API aplica as migrations do Entity Framework Core automaticamente
      ao iniciar - voce nao precisa rodar nenhum comando de migration a
      parte, o banco ja fica pronto para uso.

    Depois de subir, a API fica disponivel em: http://localhost:8080

OPCAO B - Rodando localmente, sem Docker para a API (precisa de um Postgres
acessivel de algum jeito - pode ser o mesmo do compose, so o banco)

    1. Suba so o banco: docker compose up postgres
       (ou aponte para uma instancia de Postgres sua, se preferir)
    2. Se precisar, ajuste a connection string em
       src/CashFlow.Api/appsettings.json (chave
       ConnectionStrings:CashFlowDatabase) - por padrao ela ja aponta para
       localhost:5432, que e onde o compose expoe o banco.
    3. Execute:

       dotnet run --project src/CashFlow.Api

    Por padrao (ver src/CashFlow.Api/Properties/launchSettings.json), a
    aplicacao sobe em http://localhost:5080, com
    ASPNETCORE_ENVIRONMENT=Development ja configurado.

--------------------------------------------------------------------------------
2. TESTANDO PELO SWAGGER (o jeito mais facil, recomendo comecar por aqui)
--------------------------------------------------------------------------------

O Swagger UI so fica disponivel quando ASPNETCORE_ENVIRONMENT=Development
(isso e desligado de proposito em producao, por seguranca - nao e desejavel
deixar uma pagina que permite disparar chamadas contra a API exposta
publicamente).

    - Via Docker Compose: http://localhost:8080/swagger
    - Via dotnet run local: http://localhost:5080/swagger

O que voce vai encontrar la:
    - Os dois grupos de endpoints (Lancamentos e Saldos Diarios), cada um
      com o metodo HTTP, os parametros esperados e os codigos de resposta
      possiveis (200, 201, 400, 404) com uma descricao de cada um. Essa
      descricao nao foi escrita "a mao" direto no Swagger - ela vem dos
      proprios comentarios /// que estao em cima de cada metodo do
      controller (em LaunchesController.cs e DailyBalancesController.cs),
      exportados automaticamente para a UI. Ou seja: a documentacao nunca
      fica desatualizada em relacao ao codigo, porque ela literalmente
      nasce do codigo.
    - O botao "Try it out" permite montar o corpo da requisicao e executar
      a chamada direto do navegador, sem precisar de Postman, Insomnia ou
      qualquer outra ferramenta externa.

--------------------------------------------------------------------------------
3. ENDPOINT: REGISTRAR UM LANCAMENTO
--------------------------------------------------------------------------------

    POST /api/v1/launches
    Content-Type: application/json

    Corpo esperado:
    {
      "description": "Venda de produto X",
      "amount": 150.75,
      "type": "Credit",
      "launchDate": "2026-08-14"
    }

    O que cada campo significa:
    - description : texto, obrigatorio, no maximo 200 caracteres.
    - amount       : valor decimal, obrigatorio, precisa ser maior que zero.
    - type         : "Credit" (entrada) ou "Debit" (saida). Optei por
                     gravar e trafegar isso como texto, nao como numero,
                     para o dado ficar legivel por si so, tanto no Swagger
                     quanto para quem estiver consumindo a API.
    - launchDate   : opcional, no formato AAAA-MM-DD. Se voce nao enviar,
                     assume a data atual (UTC). Nao pode ser uma data no
                     futuro.

    Exemplo via curl (Docker Compose, porta 8080):

        curl -i -X POST http://localhost:8080/api/v1/launches \
          -H "Content-Type: application/json" \
          -d '{"description":"Venda balcao","amount":150.75,"type":"Credit","launchDate":"2026-08-14"}'

    Resposta esperada: 201 Created, com o corpo assim:

    {
      "id": "b3f1c2...-...",
      "description": "Venda balcao",
      "amount": 150.75,
      "type": "Credit",
      "launchDate": "2026-08-14",
      "createdAtUtc": "2026-08-14T19:00:00Z"
    }

    Para ver o erro de validacao funcionando (400 Bad Request), tente
    enviar um valor invalido de proposito:

        curl -i -X POST http://localhost:8080/api/v1/launches \
          -H "Content-Type: application/json" \
          -d '{"description":"","amount":-10,"type":"Credit"}'

    A resposta vem no formato padrao de erro (application/problem+json),
    com uma mensagem clara para cada campo que falhou:

    {
      "type": "https://httpstatuses.io/400",
      "title": "Ocorreram um ou mais erros de validação.",
      "status": 400,
      "detail": "...",
      "errors": {
        "Description": ["A descrição é obrigatória."],
        "Amount": ["O valor deve ser maior que zero."]
      }
    }

--------------------------------------------------------------------------------
4. ENDPOINT: CONSULTAR LANCAMENTOS DE UMA DATA
--------------------------------------------------------------------------------

    GET /api/v1/launches?date=2026-08-14

    curl "http://localhost:8080/api/v1/launches?date=2026-08-14"

    Resposta esperada: 200 OK com uma lista de lancamentos. Se nao houver
    nenhum lancamento naquela data, a resposta e uma lista vazia ([]), e
    nao um erro 404 - afinal, "nao ter lancamento" e um resultado valido
    para essa consulta, nao uma falha.

--------------------------------------------------------------------------------
5. ENDPOINT: CONSULTAR O SALDO CONSOLIDADO DE UM DIA
--------------------------------------------------------------------------------

    GET /api/v1/daily-balances/2026-08-14

    curl -i "http://localhost:8080/api/v1/daily-balances/2026-08-14"

    Resposta esperada (200 OK), assumindo que a consolidacao ja rodou:

    {
      "referenceDate": "2026-08-14",
      "totalCredits": 150.75,
      "totalDebits": 0,
      "closingBalance": 150.75,
      "status": "Consolidated",
      "consolidatedAtUtc": "2026-08-14T19:00:02Z",
      "failureReason": null
    }

    Um detalhe importante para nao se assustar ao testar: a consolidacao
    acontece em segundo plano, de forma assincrona, disparada
    automaticamente logo depois do POST de um lancamento. Ou seja, se voce
    chamar esse GET meio segundo depois do POST, e possivel (ainda que raro
    - o worker e rapido) que o saldo ainda nao exista. Se isso acontecer, a
    resposta e 404 Not Found. Para um teste totalmente previsivel, sem
    depender de tempo, use o endpoint de consolidacao manual da secao 6
    logo antes de consultar.

    E exatamente assim que os testes de integracao fazem isso: eles chamam
    o endpoint de consolidacao manual explicitamente, em vez de esperar o
    worker em segundo plano, para o teste nunca ficar dependente de timing.

--------------------------------------------------------------------------------
6. ENDPOINT: FORCAR A (RE)CONSOLIDACAO DE UMA DATA (MANUAL)
--------------------------------------------------------------------------------

    POST /api/v1/daily-balances/2026-08-14/consolidate

    curl -i -X POST "http://localhost:8080/api/v1/daily-balances/2026-08-14/consolidate"

    Resposta esperada: 200 OK, ja com o saldo recem-calculado no corpo da
    resposta (mesmo formato do endpoint anterior). Diferente da
    consolidacao automatica, esse endpoint e sincrono - ele calcula e ja
    devolve o resultado na mesma chamada, o que e util para demonstracoes
    e para recuperar manualmente uma data especifica sem precisar esperar.

    Chamar esse endpoint duas vezes seguidas para a mesma data e seguro: o
    resultado final e sempre o mesmo, porque a consolidacao recalcula tudo
    do zero a cada vez (e por isso que ela e chamada de idempotente).

--------------------------------------------------------------------------------
7. ENDPOINT: RELATORIO DE SALDO DIARIO EM UM INTERVALO DE DATAS
--------------------------------------------------------------------------------

    GET /api/v1/daily-balances?startDate=2026-08-01&endDate=2026-08-14

    curl "http://localhost:8080/api/v1/daily-balances?startDate=2026-08-01&endDate=2026-08-14"

    Resposta esperada: 200 OK com uma lista de saldos diarios, um para cada
    dia que ja tiver algum saldo (Consolidated ou Failed) dentro do
    intervalo pedido.

    Duas regras de validacao valem para esse endpoint:
    - endDate precisa ser maior ou igual a startDate.
    - o intervalo entre as duas datas nao pode passar de 366 dias (para
      evitar uma consulta absurdamente ampla).

    Para ver a validacao rejeitando um intervalo invertido:

        curl -i "http://localhost:8080/api/v1/daily-balances?startDate=2026-08-14&endDate=2026-08-01"

--------------------------------------------------------------------------------
8. HEALTH CHECK
--------------------------------------------------------------------------------

    GET /health

    curl -i http://localhost:8080/health

    Resposta esperada: 200 OK, corpo "Healthy". E util principalmente para
    orquestradores (Docker, Kubernetes) saberem se o processo da aplicacao
    esta de pe e respondendo.

--------------------------------------------------------------------------------
9. COMO DEMONSTRAR A RESILIENCIA NA PRATICA
--------------------------------------------------------------------------------

Se quiser mostrar, na pratica e nao so na teoria, que o registro de
lancamentos nao depende da consolidacao estar saudavel, um roteiro possivel:

    1. Suba tudo com "docker compose up".
    2. Registre alguns lancamentos normalmente e confirme que cada um
       responde 201 Created.
    3. Derrube o banco de dados momentaneamente:
           docker compose stop postgres
    4. Nesse momento, chamadas de registro tambem vao falhar - e importante
       ser honesto sobre isso: sem banco nenhum, nao existe lugar para
       persistir o lancamento, e essa parte nao tem como ser contornada.
       O ponto que o desafio pede para demonstrar e outro, mais especifico:
       e o subsistema de CONSOLIDACAO que pode ficar instavel sem derrubar
       o REGISTRO - nao "o banco de dados inteiro cair". Para ver esse
       cenario mais realista, o ideal e acompanhar os logs do
       ConsolidationWorker: mesmo quando a consolidacao de uma data
       especifica falha repetidamente, o retry e o circuit breaker do
       Polly absorvem essas falhas, e o lancamento em si - que ja tinha
       sido salvo antes de qualquer tentativa de consolidacao - permanece
       intacto no banco, pronto para ser reconciliado depois.
    5. Suba o banco de novo:
           docker compose start postgres
    6. Chame o endpoint de consolidacao manual (secao 6) para a data
       afetada, ou simplesmente espere a proxima passada do
       ReconciliationWorker - ele vai encontrar qualquer data com
       lancamentos mas sem saldo "Consolidated" e reenfileirar
       automaticamente, sem voce precisar fazer nada.

--------------------------------------------------------------------------------
10. TESTANDO PELOS TESTES AUTOMATIZADOS (a forma mais confiavel)
--------------------------------------------------------------------------------

Testar manualmente, como nas secoes acima, e otimo para entender e
demonstrar o comportamento. Mas a forma mais confiavel de confirmar que
tudo funciona - e que costuma pesar mais numa avaliacao tecnica - e rodar a
suite de testes automatizados:

    dotnet test CashFlow.sln

O arquivo 06-TESTES-EXPLICADOS.txt detalha cada suite, o que cada teste
cobre de fato, e os pre-requisitos para rodar os testes de integracao (eles
precisam do Docker rodando, porque usam Testcontainers para criar um
Postgres real e descartavel a cada execucao).
